# Updating this artifact

This project was generated by the **meta template** `cyan/new` — the official CyanPrint template that scaffolds artifacts. `cyanprint update` floats it to the latest version and runs a real git three-way merge (base = the old version re-executed from your recorded answers; theirs = the new version; ours = your files on disk), with rename detection:

- Files you never touched update cleanly.
- Files you edited that upstream did not change are kept.
- Files BOTH sides changed either merge line-by-line or keep standard in-file `<<<<<<<` conflict markers; the command exits non-zero listing conflicted files.

## Practice

- Run `cyanprint update .` to pull the latest scaffolding — CI workflows, the CI script, these skills, and the vendored `@cyanprint/sdk` types (`--interactive` to pick versions; `--template cyan/new` to target just this template). Let update own those files; do not hand-edit them, or you will create update conflicts.
- You own: `src/`, `cyan.yaml` metadata, your `package.json` dependencies, and your tests. Bump those yourself (e.g. `bun update`), then re-run `cyanprint test`.
- Your original answers and deterministic state persist in `.cyan_state.yaml`, so update reuses them without re-asking (only new questions prompt).
- After any change, run `cyanprint test` — every case must pass and validations must exit 0.
- If files conflict, resolve the `<<<<<<<` markers in place, then re-run `cyanprint update .` — while markers are pending, `.cyan_state.yaml` stays at the old version, and the re-run completes the move. The re-run is a fresh three-way merge from the old base, so a hunk resolved to something that overlaps the incoming change but differs from it conflicts again; safest is to take the incoming text and re-apply your own edit as a follow-up commit. Finish with `cyanprint test`.

## When a template you depend on changes (the republish cascade)

A published template **freezes its dependencies at push time**: `cyanprint push` pins every `templates:` and `resolvers:` entry — an unpinned one resolves to the latest version at that moment — and every install uses exactly those pins. So a fix in a template you list under `templates:` reaches your consumers **only after you republish**, and theirs only after their dependents republish too. Updates flow down the tree one level at a time:

1. The changed template is published first, with its tests and probes green.
2. Then each template that depends on it, in tree order — a template is republished only after everything it depends on is published.
3. Then every project generated from them (see "Projects" below).

For this template, when a dependency has published a new version:

1. **Pull it.** A pinned key (`acme/base@4: {}`) is bumped to the new version in `cyan.yaml`. An unpinned key (`acme/base: {}`) needs no edit, but this template must still be pushed again to re-pin. If a **resolver** you share with your dependencies was republished, bump its `ref: owner/name@N` in your `resolvers:` together with theirs: layers agree on a resolver only when ref, version, and config are all identical — otherwise the path falls back to last writer wins.
2. **Check that nothing was overridden.** Generate into a fresh directory (`cyanprint try . <fresh-dir> --headless --answers answers.json`) and read the `provenance:` list in `<fresh-dir>/.cyan_state.yaml`. A new `lww-override` means the highest layer's version of a conflicting path replaced the lower layers' variations wholesale: their fixes to that file never reach the result. Read `segment`, `source`, and `contributors` to see who clashed. If this template's own file replaced a dependency's, fix the cause instead of asserting the LWW — ship only the lines you add or change, declare the same resolver (same ref, version, and config) for that path, and load the file through a `Template` file scope (`Copy` files count as binary and are never resolver-merged). If the clash is between processor outputs or between two dependencies, fix it in the contributing layers that `contributors` names.
3. **Prove the status quo.** `cyanprint test .` — expected outputs, `merges:` assertions, validations, and probes (every declared feature needs a proven baseline AND a caught mutation, so CI still fails when it should). Refresh `expected/` with `cyanprint test . --update-snapshots` only after reviewing that every changed file is the dependency's intended change.
4. **Publish.** `cyanprint push .` (it re-runs the tests unless `--no-test`).
5. **Hand off** to the templates that depend on this one; they repeat these steps.

Never skip a level. A template that is not republished keeps the old pin, so nothing below it sees the fix — republish it even when its own files did not change.

Local runs (`try`, `test`) do **not** download a dependency from the registry. They find it through the `.cyan_artifact_bundles.json` index of a hydrated template, or in a directory named `examples/templates` (or `examples/template-groups`) found by walking up from the template directory or the current directory, matched by `owner`/`name` — and by `version` when the key is pinned, so the local copy's `cyan.yaml` must then carry that `version:`. Check the dependency out there, at the version you are pinning, before step 2.

### Projects

After the last template is published, each project generated from the tree:

1. **Commit first**, so the tree is clean — update merges whatever is on disk, and a clean commit makes the template's change the only diff.
2. `cyanprint update .` (`--template owner/name` to float one install; `--headless --answers answers.json` in CI). Update reads project files from disk, ignored ones included, except `.cyan_state.yaml`, `.git`, and template probe paths (`probes/**`, `probes.yaml`); if it refuses to write through a hard link (e.g. under `node_modules/` after `bun install`), delete that directory, re-run, and reinstall afterwards. A project installed from a local template path re-reads that same path as its base, so it never picks up changes — install from the registry to receive the cascade.
3. On `merge_conflicts_pending`, resolve each marked hunk and re-run `cyanprint update .` — the retry is a fresh three-way merge from the original base, so a resolution that overlaps the incoming change but differs from it conflicts again. Taking the incoming side always finishes; re-apply your own customisation afterwards as a normal commit.
4. Run CI, then commit the update. Never edit `.cyan_state.yaml` by hand — it is the merge base for every later update.
